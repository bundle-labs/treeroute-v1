## What a row is

One survey visit: a site on a date. Several surveys at one site and date are averaged. Each row has:
- keys: row_id, unit_id (ecoregion + site), group (ecoregion name), lat, lon, target_date, issue_date,
  feature_end (the last content day any feature window may read; before the issue date), mark;
- the label pct_bleached (0-100);
- the report stratum programme (Reef_Check, FRRP, McClanahan, AGRRA, Donner, or mixed);
- 5 router context columns (season at the feature cut, |lat|, MMM);
- 69 tree columns: SST heat (30), heat history (7), marine heatwaves (10), cyclones (16), ENSO anomaly (3), IOD (3).

## How the tables are made (package side, never by the engine)

```
cd D:\treeroute\coral_build\coral_tables
py -3.9 -u build_visits.py                       # stage 1: visits, marks, census (seconds)
py -3.9 -u build_tables.py --build tiny          # 4 default groups, every row canaried (3 minutes)
py -3.9 -u check_tables.py --build tiny          # contract + independent look-ahead check
py -3.9 -u build_tables.py --build full          # stage 2: the three lead files (owner command, about 30 min)
py -3.9 -u check_tables.py --build full          # (about 10 minutes)

# make_draft.py (it rewrites catalog.yaml and ban.yaml from columns.py) is NEVER run on the signed package: it
# would lose the signatures written by make_signed_coral.py.
# The split check uses the V6 (b) file in coral_build_v6b (SHA-256 a69e1c8c...), NOT coral_tables\make_split.py in
# this folder (the pre-(b) version, SHA-256 c38d76b1..., which checks V6 (a)). Its path guard (make_split.py:188-190)
# lets it read only a split.yaml under D:\treeroute\coral_build_v6b: its own copy of the development package's
# split.yaml (the same entries as this package's; only the comments differ).
py -3.9 -u D:\treeroute\coral_build_v6b\coral_tables\make_split.py --check   # V5 with no V6 exclusion (exit 1 if not)
py -3.9 -u D:\treeroute\coral_build_v6b\coral_tables\make_split.py --lead-dir D:\treeroute\coral_build\coral_data\full --check   # again after stage 2
```

## Signed answers, ruling V (2026-10-19; V6 replaced by ruling W, 2026-10-20)

The owner took every recommended answer of the coral build (OWNER_RULINGS_2026-10-06.md:97-114, "yes to all").
What each one means for this package:

- **V1 decline object.** For the neighbour kind, every decline (nowcast and each lead) falls back to the donor-row
  median (R34). Every guard and decline check of that kind uses the same median as its baseline. The grid kinds keep
  their old rule until the next engine version. The engine reads the kind from the data (R12), not from this package.
  Two details. (1) The nowcast baseline is each fold's median with that fold's group left out
  (decision_checks.json per_fold_median). Each lead's guard baseline is the guard bank's median over all kept groups,
  the guard rows' own groups included (lead.json guard.baseline_value). Each pass falls back to the same median it
  was compared with. (2) For a declined lead, the locked lead file (adoption_lead_<L>.json) records only guard_passed
  false and adopted null. The decline target (base__donor_median) and the guard baseline are written in lead.json and guard_preds.parquet,
  and the target is rebuilt from the router kind (R12, fingerprinted) at run time.
- **V2 pool tree drop.** The signed default stays: the trees of every group in a row's pool are dropped. The full run
  reports the share of rows left with no tree (n_rows_no_tree, route/neighbour.py:914).
- **V3 test window.** 2016-2019, by leaving out the 38 visits of 2020 (build_visits.py:202-203 marks them unused; they
  are not written). This departs from R3: on all the data R3 gives 2017-2020. The window was chosen after the
  yearly counts were seen (SPEC_CORAL_TABLES.md:19-21). Disclosed in exceptions.yaml (check R3). 2017-2020 is the
  declared sensitivity row (below).
- **V4 table departures.** The table departures are accepted at the coral freeze, as S21 did for the grid departures.
  Built: they are listed in TABLE_ACCEPTED_DEPARTURES (pipeline/table_run.py:58-73) and written into the run record
  as accepted_departures; TABLE_DEPARTURES is empty (:57).
- **V5 refused groups.** The 11 groups the engine defaults refuse are left out in split.yaml: 4 with 0 train rows at a
  bank cut (O13) and 8 with one site (O14; North-west Arabian Sea is both). They hold 35 test and 9 train visits.
- **V6 (b) donor-only groups (owner ruling W1, 2026-10-20, which replaces V6; D:/treeroute/coral_build_v6b/PLAN_V6B.md).** The 46 groups
  with no test row in the lead files after V5 are NOT left out. Gulf of Thailand is one: its 10 test-window visits
  have no lead-0 SST history, so none is written. They hold 1,874 train visits on 1,066 sites (111 are 2013-2015
  decision-surface rows). Their trees enter every bank, their train rows every neighbour pool and the decision
  surface; nothing is scored for them (the engine reads this from the marks: derived.json R18:donor_only).
  Brazil, Cuba and Cayman Islands, Hong Kong, New Caledonia, Gulf of Thailand and Vanuatu are among them.

### The 2017-2020 sensitivity row (declared; not built, not run)

It is reported beside the headline, never as the headline. How it would be produced, after the headline run, one
heavy job at a time:

1. Stage 1 into its OWN folder (never over coral_data\visits.parquet):
   `py -3.9 -u build_visits.py --test-years 2017-2020 --out D:\treeroute\coral_build\coral_data\sens_2017_2020`.
   The 2020 visits are then written as test rows; nothing is left out after 2020 by this rule.
2. Stage 2 and the checker read the visit table at the fixed path coral_data\visits.parquet (build_tables.py:78,
   check_tables.py:52, :332). So they first need a small option `--visits-dir DIR` (default coral_data) that sets the
   visit table, the census and the output folder. This is a builder code change; it is NOT made yet (it would change
   the builder's code hash and force a rebuild of the tiny tables, build_tables.py:104).
3. Then `build_tables.py --build full --visits-dir <sens folder>` and `check_tables.py --build full --visits-dir
   <sens folder>`.
4. `make_split.py --visits <sens folder>\visits.parquet --split <sens package>\split.yaml --write`: the V5 list and the
   donor-only count are recomputed for that window (they will differ from the headline lists).
5. A package copy coral_sens_2017_2020: its own name, store line and split.yaml; its header says "declared
   sensitivity row (V3); never the headline". The cuts move one year later (R3 gives 2020, R5 2017-2020).
6. From LIVE (the table option is installed: engine 930d961c..., 2026-10-20): check, smoke, run, at the same engine
   hash as the headline run. Reported with a not-headline reason, and declared in the coral
   pre-registration Part with these commands.
